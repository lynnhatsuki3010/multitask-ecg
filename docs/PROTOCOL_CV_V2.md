# Protocol v2 — 10-fold cross-validation of the infarct head

Status: **registered.** The commit that adds this file is the registration: its
timestamp precedes every result it governs, and the runner refuses to start when the
tracked code differs from a commit (section 9). Nothing below may be changed after the
first v2 run; amendments go into a new, dated section at the end and are reported as
such.

Earlier results (single split, 10 seeds, checkpoint by validation IMI AUPRC) are
**exploratory**. They motivated the hypotheses below and are not reused as
evidence for them.

## 1. Questions

1. Does the clustered token layout improve inferior-MI (IMI) localization over the
   same model without it, and over a shared backbone, when estimated out-of-fold on
   all of PTB-XL?
2. Is the gain specific to the layout, or do label-structure heads that encode the
   annotation convention (IMI and ILMI never co-occur) obtain it without changing
   which leads each label sees?
3. How does the layout compare with published backbones retrained under the same
   protocol?
4. Mechanism: does the IMI head of each arm use V5–V6 to reject ILMI?

## 2. Data

* PTB-XL 1.0.1, 500 Hz, 10 s, 13 labels, SCP likelihood ≥ 50 (unchanged).
* **LBBB = CLBBB ∪ ILBBB.** LAFB (left anterior fascicular block) is no longer folded
  into LBBB: it is a fascicular block, not a bundle branch block. 698 records whose
  only selected-label code was LAFB now carry none of the 13 labels and stay in the
  data as negatives for every label. The four MI labels are unchanged.
* Built by `scripts/01_build_metadata.py --config configs/cv/cv_layout.yaml`;
  `dataset_policy.json` records the label-group override and is audited at train time.

## 3. Splits

* 10-fold CV over PTB-XL `strat_fold` (patient-disjoint by construction).
* Fold k: test = k, validation = k mod 10 + 1, train = the other eight.
* Written by `scripts/26_make_cv_splits.py`, which checks that no patient crosses
  sets and that every record is a test record exactly once.

## 4. Arms

| Arm | Config | Role |
|---|---|---|
| `cv_layout` | ARCH-13 | **proposed**: fully decoupled + clustered token layout, no sibling contrast |
| `cv_decoupled` | ARCH-09 | same model without the layout |
| `cv_shared` | ARCH-05 | shared CNN + Transformer |
| `cv_partial_layout` | ARCH-17 | shared backbone + clustered layout |
| `cv_contrast` | ARCH-16 | mechanism probe: sibling difference without the layout |
| `cv_pairsoft` | ARCH-09 + pairwise softmax head | label-structure baseline |
| `cv_hier` | ARCH-09 + territory × extension head | label-structure baseline |
| `cv_xresnet1d101` | PTB-XL benchmark backbone, plain MI head | published baseline |
| `cv_inception1d` | PTB-XL benchmark backbone, plain MI head | published baseline |
| `cv_ecgtransform` | ECGTransForm backbone, plain MI head | published baseline |

Configs are generated by `scripts/make_cv_configs.py`. "Plain MI head" means no
anatomical lead-group encoders, so published baselines are not given the idea under
test. Deviations of the published backbones from their source are listed in
`src/models/baselines.py`.

## 5. Training

* One run per arm per fold; seed `3000 + k` for fold k. These seeds were never used
  in the exploratory study.
* **Learning-rate budget.** Before the CV runs, every arm gets the same grid,
  lr ∈ {1e-4, 3e-4, 1e-3}, trained on fold 1 (validation = fold 2) with seed 3001, and
  keeps the lr whose run reaches the lowest validation loss (`loss/total`, minimum
  over epochs; ties go to the smaller lr). Selection is done by
  `scripts/29_select_lr.py`.
* **The chosen grid run is the arm's fold-1 CV run.** It has exactly the
  configuration, data and seed the fold-1 run would have had, so it is not trained
  twice. The other two grid runs per arm are moved aside and their test predictions
  are not analysed. Total: 10 arms × 3 lr on fold 1 + 10 arms × 9 folds = 120 trainings,
  100 of which form the CV study.
* **Epochs:** 15 for the project's arms (as in the exploratory study), 30 for the three
  published backbones, which are trained from scratch here and whose source training
  runs longer. Checkpoint selection by validation loss makes surplus epochs harmless.
* Loss, augmentation, optimiser and schedule as in the exploratory study.
* **Checkpoint selection: lowest total validation loss** (`monitor_metric: val_loss`),
  not IMI AUPRC, so selection and endpoint are different quantities.
* Calibration (temperature per task, threshold per class) is fitted on each fold's
  validation set and applied to its test set.

## 6. Endpoints

Computed on the pooled out-of-fold (OOF) test predictions by
`scripts/28_cv_aggregate.py`.

* **Primary:** OOF IMI AUPRC.
* **Secondary:** OOF IMI-head AUROC for IMI-only vs ILMI-only records; ILMI→IMI rate
  at each fold's calibrated threshold; OOF AUPRC of ILMI, ASMI, AMI and their macro;
  inferior-wall AUPRC (IMI or ILMI).
* **Mechanism (descriptive):** the same pairwise AUROC and ILMI→IMI rate with V5–V6
  zeroed and, as control, with V3–V4 zeroed.

## 7. Hypotheses and tests

Primary family (Holm across the three):

* H1: `cv_layout` > `cv_decoupled` in OOF IMI AUPRC.
* H2: `cv_layout` > `cv_shared`.
* H3: `cv_layout` ≠ best of {`cv_pairsoft`, `cv_hier`} (two-sided).

All other comparisons are descriptive.

* 95% CIs: bootstrap over patients (2,000 draws), all of a patient's records drawn
  together. Paired comparisons use the same draws for both arms.
* Fold-level test: exact two-sided Wilcoxon over the ten per-fold differences.
* A hypothesis is supported when the patient-bootstrap CI of the difference excludes 0
  in the stated direction (either direction for H3) and the Holm-adjusted fold-level
  p < 0.05. `scripts/28_cv_aggregate.py` prints this table first.
* H3 compares with whichever of `cv_pairsoft`, `cv_hier` has the higher OOF IMI AUPRC.

**Sensitivity: fold 2.** The learning rate was chosen on fold 2's labels (validation
set of fold 1), and fold 2 is the test set of CV fold 2. Every endpoint and test is
therefore also reported with fold 2 removed (`28_cv_aggregate.py --exclude-folds 2`).
Conclusions are drawn from the full ten folds; a conclusion that does not survive the
removal of fold 2 is reported as such.

## 8. What will be reported regardless of outcome

Every arm on every endpoint, including arms that beat the proposed model and
endpoints where the layout does not help (ILMI, AMI are expected not to). Failed or
repeated runs are listed with their cause.

## 9. Execution

* `scripts/cloud/run_cv.sh` runs the study end to end: data, lr grid, selection,
  the CV runs, calibration, prediction dumps and both aggregations.
* It builds the data if missing and stops unless the labels and the thirty split files
  match `configs/cv/data_sha256.txt` (written from the data used to design the study).
* It stops when tracked code under `src/`, `scripts/` or `configs/` differs from the
  checked-out commit, and records that commit, the GPU, driver and package versions in
  `logs/cv_v2/env_*.txt`.
* A job that crashes is retrained from scratch with the same seed when the runner is
  started again; partially trained runs are never resumed or mixed.
